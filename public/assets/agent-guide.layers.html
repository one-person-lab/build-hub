参考架构 · 四层

一次 Agent 请求跑下来，路上有哪几层

这是通用参考架构，不是微服务清单。早期四层全塞在一个应用里完全可以，复杂度涨上来再拆——但每一层该管的事，一样都不能少。

业务入口用户从哪进来
自然语言对话、指令
表单结构化提交
业务事件状态变化触发
API系统对系统
Agent 运行时核心：决定下一步
任务规划拆解任务、选下一步
模型与 Prompt推理、决策、模型路由
上下文管理历史、检索、状态、压缩
工具与编排Tool、Workflow、重试、审批
执行结果反馈 · 状态更新 · 下一轮决策——这一圈能跑起来，才叫 Agent；跑不起来，就还是一次调用。
业务能力层它的手，不是新写的
业务 API订单、设备、用户、任务
知识检索RAG、数据库、文档
外部工具搜索、第三方服务、MCP
执行服务任务调度、异步、设备控制
横向工程保障贯穿上面三层
评测与回归 Trace 与日志 权限与安全 超时与重试 成本与延迟 版本管理

最容易被跳过的是最后那一条横带。它不在演示里，但出事的时候只有它能回答「为什么它当时做了这个决定」。

业务入口自然语言、表单、业务事件、API。四种入口的权限口径必须一样。
Agent 运行时任务规划、模型与 Prompt、上下文管理、工具与编排；结果反馈回来推下一轮。
业务能力层业务 API、知识检索、外部工具、执行服务。这些本来就该存在。
横向工程保障评测与回归、Trace 与日志、权限与安全、超时与重试、成本与延迟、版本管理。
