架构选型 · 四种做法

下一步由谁决定，决定你要背多少责任

按「下一步由谁决定」分，常用的就这四种。编号越靠后，模型拿走的决定越多，你要补回来的控制也越多——所以够用就停在靠前的那一档。

做法一

单次模型调用

没有下一步

输入 → 提示词 → 输出。分类、摘要、文案、信息提取都够用。

代价：一问一答，办不了需要多步推进的事。

做法二

固定工作流

代码写死顺序

模型只做其中一步的理解或生成。适合审核、报告、内容流水线。

代价：可预测、好测试，但分支一变就得回去改代码。

做法三

工具调用型 Agent

模型看完工具结果再定

调工具 → 拿结果 → 更新上下文 → 再决定，直到完成或触发停止条件。

代价：必须设停止条件、次数上限，轨迹要查得到。

做法四

多 Agent 协作

主 Agent 派活

研究、规划、执行、审核各由一个专业 Agent 承担，能并行的并行。

代价：成本、调试难度、协作失败风险一起翻倍。

每往后挪一档，多背一份责任

做法一提示词质量、输出格式
做法二分支覆盖、每一步的回归用例
做法三工具权限、停止条件、失败怎么回收
做法四交接协议、成本上限、谁有最终裁量

选型看的是「下一步由谁决定」，不是哪个名字热门。前一档能解决干净的，就别往后挪。

做法一 · 单次模型调用没有下一步。适合分类、摘要、提取。办不了多步的事。
做法二 · 固定工作流代码写死顺序，模型只做一步。可预测好测试，分支一变要改代码。
做法三 · 工具调用型 Agent模型看完工具结果再定下一步。要设停止条件、次数上限、轨迹可查。
做法四 · 多 Agent 协作主 Agent 派活，专业 Agent 各管一段。成本、调试、协作失败都翻倍。
往后挪一档，多背一份责任提示词 → 分支覆盖 → 工具权限与停止条件 → 交接协议与最终裁量。
